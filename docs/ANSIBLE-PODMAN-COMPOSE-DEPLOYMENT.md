# 🛡️ CmsForNerd Production Podman-Compose & BunkerWeb Deployment Guide (v4.1.0)
# docs/ANSIBLE-PODMAN-COMPOSE-DEPLOYMENT.md

This document serves as the official blueprint and operational handbook for deploying **CmsForNerd** into a hardened production
environment using **Ansible** and **Podman-Compose** with **BunkerWeb** as the first line of defense.

---

## 1. Architectural Blueprint

The production architecture implements a hardened, rootless multi-layered container configuration:

```text
                  [ Internet / Host Ports 80 & 443 ]
                                 │
                                 ▼
         ┌──────────────────────────────────────────────┐
         │                 BUNKERWEB                    │
         │  (WAF & Security Shield, Rootless, Port 80)  │
         └───────────────────────┬──────────────────────┘
                                 │ (Container Network)
                                 ▼
         ┌──────────────────────────────────────────────┐
         │                CMS-NGINX                     │
         │  (Static Asset Server & Proxy, Port 80)       │
         └───────────────────────┬──────────────────────┘
                                 │ (FastCGI Protocol)
                                 ▼
         ┌──────────────────────────────────────────────┐
         │                 CMS-PHP                      │
         │     (Custom PHP-FPM 8.5 Container, Port 9000)│
         └──────────────────────────────────────────────┘
```

---

## 2. Security and Identity Standard

- **Production User & Group**: `dsom-admin` utilizing UID:GID **`2001:2001`**.
- **Rootless Execution**: All containers are executed in user space via rootless Podman, eliminating root compromise vectors.
- **Storage Sovereignty**: Enforces absolute ownership mapping on physical host directories via `--userns=keep-id` (`userns_mode: keep-id`
  and `user: "2001:2001"` in Docker-Compose). This guarantees that files written inside the containers map directly to UID `2001` on disk,
  making them secure and extremely easy to back up.
- **Systemd Lingering**: Systemd lingering is enabled via `loginctl` to ensure that rootless containers and services persist after the
  Ansible SSH session disconnects or when the server restarts.

## 3. Directory Layout on Physical Disk

All files and logs are written directly to host directories to ensure high availability and effortless backup routines:

| Directory Path | Mapped Container Target | Purpose |
| :--- | :--- | :--- |
| `/opt/cmsfornerd` | `/opt/cmsfornerd` | Root project directory |
| `/opt/cmsfornerd/bunkerweb/data` | `/var/lib/bunkerweb` | Persistent BunkerWeb cache & threat intelligence |
| `/opt/cmsfornerd/bunkerweb/configs`| `/etc/bunkerweb` | Dynamic configurations generated by BunkerWeb |
| `/opt/cmsfornerd/nginx` | `/etc/nginx/conf.d` | Custom, read-only Nginx routing and block rules |
| `/opt/cmsfornerd/php-fpm` | `/usr/local/etc/php-fpm.d` | Hardened PHP-FPM pool configuration |
| `/opt/cmsfornerd/codes` | `/var/www/html` | Main CmsForNerd codebase (writable by PHP, read-only by Nginx)|

## 4. The "Trinity of Safety" Interlocks

The local/remote orchestration wrapper script `tools/deploy-prod.sh` strictly enforces three layers of safety gates:

1. **Status Probe**: Automatically scans local control machine prerequisites (Ansible, Git, and Composer) and executes the
   `composer lab-check` static analysis suite (PHPStan Level 8) on the source files to ensure no broken code is compiled or pushed.
2. **Sovereign Gate**: Scans the inventory to guarantee that the unprivileged target is exactly configured as `dsom-admin:2001:2001`,
   rejecting execution if unauthorized identities or permissions are found.
3. **Sudo Lock**: Ensures all root privilege escalation (`become: true` in Ansible) is eliminated at the play level and strictly scoped
   to explicit host-foundation tasks (setting up OS-level packages, Sysctl, and systemd service creation), while user-space tasks run
   with unprivileged user-space escalation or without privilege escalation.

## 5. Playbook Inventory and Variables

### 5.1 Playbook Entry Point: `playbooks/deploy_prod_compose.yml`
This playbook orchestrates the OS cache update, loads the system-hardening `common` role, and triggers the `podman_prod` role.

### 5.2 Default Role Variables: `playbooks/roles/podman_prod/defaults/main.yml`

```yaml
podman_cms_user: dsom-admin
podman_cms_uid: 2001
podman_cms_group: dsom-admin
podman_cms_gid: 2001

project_path: /opt/cmsfornerd
bunkerweb_path: "{{ project_path }}/bunkerweb"
nginx_path: "{{ project_path }}/nginx"
php_fpm_path: "{{ project_path }}/php-fpm"
codes_path: "{{ project_path }}/codes"

php_version: "8.5"
cms_domain: "cmsfornerd.local"
compose_project_name: "cmsfornerd"
bunkerweb_image: "docker.io/bunkerity/bunkerweb:1.5.8"
nginx_image: "docker.io/library/nginx:1.27"
```

## 6. Execution Instructions

To execute a secure, production-grade deployment, run the wrapper script from the repository root:

```bash
# Execute with full safety verification
bash tools/deploy-prod.sh
```

To run the playbook manually or with specific tags:

```bash
# Execute using specific tags (e.g. only template files)
ansible-playbook playbooks/deploy_prod_compose.yml -i inventory/hosts.prod.yml --tags "containers"
```

## 7. High Availability & Automation

To ensure that the Podman-Compose stack automatically boots on machine restarts and recovers gracefully, a user-level Systemd service is
automatically deployed for the `dsom-admin` user:

- **Service Path**: `/home/dsom-admin/.config/systemd/user/cmsfornerd-pod.service`
- **Enable command**: Built-in automatically in the Ansible role tasks using `ansible.builtin.systemd` in `user` scope.

To monitor or manage the service status on the production node:

```bash
# Log in as the dsom-admin user or become user
sudo -u dsom-admin -i

# Verify systemd user services
systemctl --user status cmsfornerd-pod

# Tail container logs
journalctl --user -u cmsfornerd-pod -f
```
